# Поддерживаемая область Finspace 1.0

Это контракт поддержки, а не описание возможностей. Он отвечает на один вопрос: **что владелец
сервера вправе считать работающим и восстановимым в версии 1.0, а что — нет.** Всё, чего здесь
нет, не поддерживается; всё, что названо неподдерживаемым, названо так намеренно.

Документ описывает только уже реализованное и проверенное в этом репозитории. Он не содержит
обещаний на будущее.

Процедура релиза и гейт release candidate — [release.md](release.md).

## 1. Хост и развёртывание

| Что | Поддерживается |
|---|---|
| ОС сервера | self-hosted Linux (проверялось на Ubuntu) |
| Контейнеры | Docker Engine + плагин Docker Compose **2.24.4+** |
| Команда production | только repository-managed wrapper `finspace-compose` |
| Топология | `docker-compose.yml` + `compose.production.yml` из **того же** checkout |
| База данных | PostgreSQL 17 в конфигурации поддерживаемого compose |
| Кэш и счётчики | Redis 8 в конфигурации поддерживаемого compose |
| Автоматизации | n8n 2.30.5 — **опционально**, приложение работает без него |
| TLS, reverse proxy, Tailscale | внешние по отношению к Finspace; их настройка — зона хоста |

Версия Compose не произвольная: `compose.production.yml` использует `!override` и `!reset`, а они
появились в 2.24.4. Базовый `docker-compose.yml` сам по себе — конфигурация разработки
(source mounts, `--reload`, dev-режим frontend) и **production-установкой не является**.

PostgreSQL, Redis, Adminer и n8n не публикуются наружу ни при каких обстоятельствах. Adminer
остаётся диагностическим инструментом на loopback и не входит в поддерживаемую production-поверхность.

## 2. Установка

Поддерживается ровно один путь: [production-install.md](production-install.md) на чистом Linux-сервере.

- разворачивается **точный аннотированный релиз**, а не плавающая ветка;
- `.env` создаёт оператор; в Git он не попадает никогда;
- host-only конфигурация (`/etc/finspace/backup.env`, ключи) — `root:root`, режим `0600`;
- wrapper устанавливается из репозитория (`scripts/install-finspace-compose.sh`) в
  `/usr/local/bin/finspace-compose`;
- запись runtime-каталогов готовится `scripts/prepare-runtime-storage.sh`.

Не поддерживается установка «поверх» неизвестного состояния, ручная сборка топологии из отдельных
`docker run` и внешняя копия production-оверлея вне checkout.

## 3. Обновление и откат

Контракт — [upgrade.md](upgrade.md).

- миграции только **вперёд**: `alembic upgrade head` из образа целевого релиза;
- `alembic downgrade` **не является** механизмом отката и не поддерживается как штатная операция;
- проверенная восстановлением копия создаётся **до** обновления;
- откат описан тремя случаями (CASE A/B/C), и в общем случае это восстановление из копии, а не
  обратная миграция.

## 4. Backup и аварийное восстановление

- источник истины для восстановления финансов — **дамп PostgreSQL** (`pg_dump --format=custom`)
  вместе с manifest и SHA-256;
- backup set проверяется восстановлением, а не только фактом создания файла;
- **секреты хранятся вне backup**: `.env` не входит в набор, не печатается и не логируется.
  Их сохранность — отдельная обязанность владельца;
- Redis считается **одноразовым**: его содержимое не восстанавливается и не требуется для
  восстановления финансовых данных;
- n8n — **опциональный холодный архив**; отсутствие архива не блокирует восстановление приложения;
- для приёмки релиза обязательны обе процедуры: копия на **отдельном хосте** (F003) и учение по
  восстановлению в **чистой среде** (F004).

Подробности: [backup-and-restore.md](backup-and-restore.md),
[disaster-recovery-drill.md](disaster-recovery-drill.md).

Вторая директория на том же диске **не является** вторым доменом отказа и не засчитывается как F003.

## 5. Данные

- PostgreSQL — единственный источник истины по финансовым данным и истории;
- staging-файлы импорта имеют собственный жизненный цикл и освобождаются только через F010;
- приёмочные артефакты и отчёты оператора хранятся на хосте и в Git не попадают;
- границы удержания, владельцы и запреты перечислены в [data-lifecycle.md](data-lifecycle.md);
- порога «база слишком большая» нет и не будет: бюджет диска знает только владелец сервера.

Автоматического удаления финансовых данных в 1.0 нет ни в одном сценарии.

## 6. Браузер и клиент

Frontend собран на Next.js 16 и React 19. Отдельного `browserslist` в проекте нет, матрица версий
браузеров **не тестировалась**, поэтому и обещания такой матрицы здесь нет.

Поддерживается: **современные desktop-браузеры с автообновлением** (Chromium-совместимые, Firefox,
Safari) в актуальной версии. Интерфейс русскоязычный (`lang="ru"`).

Не поддерживается: браузеры без автообновления, конкретные старые версии, режимы совместимости.

## 7. Мобильные устройства

Отдельных мобильных приложений нет. PWA-манифеста и service worker в проекте нет, установка «как
приложение» не поддерживается и не заявляется.

Мобильный браузер может открыть интерфейс, но мобильная вёрстка и мобильные сценарии в 1.0 не
входят в поддерживаемую область.

## 8. Аутентификация и совместная работа

Реализованная модель — **workspace с участниками**:

- пароль 10–128 символов, Argon2id, plaintext нигде не сохраняется;
- короткоживущий access JWT + ротируемый refresh token в `HttpOnly`-cookie; повторное
  использование отозванного token отзывает сессии;
- роли: `viewer` (чтение), `editor` (изменение финансовых данных, импорт, rollback),
  `owner` (участники и критические действия);
- workspace выбирается заголовком `X-Workspace-ID` в пределах membership пользователя; workspace из
  тела запроса не считается доверенным.

**MFA в 1.0 нет.** Подтверждения email как обязательного шага входа нет. Публичная регистрация
управляется `ALLOW_REGISTRATION` и на сервере, доступном не только владельцу, должна быть выключена.

Модель рассчитана на семью с доверенными участниками за приватной сетью, а не на публичный
многопользовательский сервис.

## 9. Интеграции

| Интеграция | Статус |
|---|---|
| Google Sheets через Apps Script Bridge | основной Google-провайдер, поддерживается |
| Google OAuth / Cloud Console | опционально, по умолчанию выключено (`GOOGLE_OAUTH_ENABLED=false`) |
| n8n | опционально; автоматизации и Telegram работают через него |
| Telegram | только через n8n; отдельной прямой интеграции нет |
| Импорт CSV/XLSX | поддерживается, размер и число строк ограничены настройками |

Прямых подключений к банкам, платёжным провайдерам и агрегаторам в 1.0 нет.

## 10. Что не поддерживается в 1.0

- Kubernetes и любой оркестратор, кроме Docker Compose;
- PostgreSQL в режиме высокой доступности, репликация, failover;
- многоузловой кластер приложения и горизонтальное масштабирование;
- эксплуатация как управляемого SaaS и мультиарендность;
- автоматический downgrade схемы;
- Windows как production-сервер (разработка на Windows поддерживается, эксплуатация — нет);
- backup без копии на отдельном хосте;
- автоматическое депонирование секретов (secret escrow) и их восстановление из backup;
- MFA;
- мобильные приложения и PWA;
- публикация PostgreSQL, Redis, Adminer или n8n наружу.

## 11. Известные ограничения

Это **не блокеры релиза**. Они зафиксированы, измеряются гейтами и не мешают эксплуатации на
домашних объёмах данных. Каждый идентификатор ниже присутствует в документе релиза
машинно-читаемо: `backend/scripts/release_evidence.py` публикует их в свидетельстве release
candidate, а `backend/scripts/validate_docs.py` завершает гейт ошибкой, если этот раздел перестаёт
их упоминать.

### `transaction-page-n-plus-1`

Страница операций стоит примерно **3,3 SQL-запроса на возвращённую строку**: `transaction_response`
делает отдельный запрос splits на каждую операцию и догружает её счёт и категорию по одному. При
странице в 200 строк это около 625 запросов.

Обнаружено F014. Число запросов **не растёт** с объёмом истории — только с размером страницы,
поэтому на домашних объёмах это не блокер. Гейт помечает такие сценарии как `known defect` и не даёт
ситуации ухудшиться. Исправление — отдельная задача, и вместе с ним нужно снизить границу
`TRANSACTION_PAGE_QUERIES_PER_ROW`.

### `aggregate-materialisation`

`calculate_balances` и `calculate_summary` загружают все подходящие операции в Python вместо
агрегации в SQL. Число SQL-запросов при этом остаётся постоянным, растёт только объём загруженных
строк.

Обнаружено F014. На текущих объёмах безопасно; преждевременная оптимизация не выполнялась.

## 12. Блокеры релиза 1.0

Это **другая категория**, и смешивать её с разделом 11 нельзя. Пока хотя бы один пункт открыт,
гейт release candidate возвращает `RELEASE STATUS: BLOCKED`, и тег `local-v1.0.0` не создаётся.

| Блокер | Состояние | Причина |
|---|---|---|
| F003 — физическая приёмка off-host backup | **отложено** | хранилище/NAS в homelab не введено |
| F004 — приёмка восстановления в чистой среде | **отложено** | чистая DR-среда в homelab не готова |
| Открытые дефекты P0/P1 | подтверждается оператором | 1.0 не выпускается с открытым P0 или P1 |

Инженерная часть при этом может быть полностью зелёной: это нормальное и ожидаемое состояние, а не
поломка. Порядок приёмки и формат свидетельств — [release.md](release.md).
