# Жизненный цикл данных: что растёт, кому принадлежит и что с этим делать

Документ отвечает на шесть вопросов оператора без чтения исходного кода:

1. что занимает место;
2. какие данные являются источником истины;
3. что можно освобождать;
4. что нельзя удалять никогда;
5. какой существующий механизм отвечает за каждую категорию;
6. как безопасно посмотреть текущее состояние.

> [!IMPORTANT]
> Здесь **нет** автоматического удаления. Всё, что описано ниже, либо уже имеет владельца
> (существующий механизм), либо не удаляется вовсе. Отчёты только измеряют.

Порогов «база слишком большая» тоже нет и не будет: 1 ГБ и 10 ГБ одинаково законны, бюджет
диска знает только владелец сервера. Предупреждения выдаются лишь при нарушении контракта —
неклассифицированная таблица, нечитаемый управляемый каталог, **неполный подсчёт**,
испорченные метаданные.

## 1. Как посмотреть

С хоста, целиком (файловая система + БД + staging импорта):

```bash
sudo /opt/finspace/scripts/data-lifecycle-report.sh
```

Только PostgreSQL, из контейнера:

```bash
cd /opt/finspace
sudo finspace-compose run --rm --no-deps backend python scripts/data_lifecycle_report.py
sudo finspace-compose run --rm --no-deps backend python scripts/data_lifecycle_report.py --json
```

Оба отчёта **только читают**: транзакция БД переводится в `READ ONLY` и ограничивается по
времени, строки таблиц не выбираются, файлы не открываются, имена файлов не печатаются.
Режима удаления нет.

Сравнение во времени делается снаружи — сохраните два снимка и сравните их:

```bash
sudo finspace-compose run --rm --no-deps backend python scripts/data_lifecycle_report.py --json \
  > "/opt/finspace/data/acceptance/data-lifecycle-$(date -u +%Y-%m-%dT%H%M%SZ).json"
```

Отдельной таблицы для истории отчётов намеренно не заведено.

## 2. Полная опись

| домен | расположение | источник истины | почему растёт | владелец retention | действие оператора | значение для DR |
|---|---|---|---|---|---|---|
| Финансовые данные и их provenance | PostgreSQL: `transactions`, `transaction_splits`, `accounts`, `categories`, `payees`, `budget_*`, `goals*`, `month_close*`, `account_reconciliation*`, `import_batches`, `import_rows`, `recurring_rule*`, `users`, `workspaces` | **да** | ввод и импорт операций | **никакого** — только явное действие пользователя в приложении | ничего не удалять; при росте смотреть индексы и объём импортов | **полностью** входит в dump |
| Операционное состояние и доказательства | PostgreSQL: `audit_log`, `auth_sessions`, `automation_runs`, `sync_outbox`, `sync_inbox`, `sync_conflicts`, `sync_runs`, `google_*`, `service_*`, `telegram_*`, `categorization_apply_*`, `goal_command_results` | да (для аудита) | активность: входы, синхронизации, автоматизации | **никакого сегодня**; строки логически истекают/отзываются, но не удаляются | наблюдать; политика удержания — отдельное продуктовое решение, а не побочный эффект уборки | входит в dump |
| Производные предпросмотры категоризации | PostgreSQL: `categorization_previews`, `categorization_preview_items` | нет | пакетные предпросмотры категоризации | **worker `categorization-prune`**, настройки `CATEGORIZATION_PRUNE_*` | ничего; при подозрении смотреть `categorization_prune_cycle_finished` в логах | входит в dump; восстановление не зависит от них |
| Том PostgreSQL | Docker volume `finspace_postgres_data` | **да** | всё вышеперечисленное + WAL и индексы | PostgreSQL (autovacuum) | **никогда не трогать содержимое тома вручную** | это и есть база |
| Staging импорта | `/opt/finspace/data/imports` | нет | загруженные CSV/XLSX | **F010**, `scripts/import_staging_reclaim.py` | осмотр, затем `--apply`; см. [import.md](import.md#освобождение-staging-reclamation) | не резервная копия |
| Свидетельства оператора | `/opt/finspace/data/acceptance` | нет (но ценно) | отчёты DR-учений, снимки счётчиков | **никакого** — только оператор | архивировать вручную, когда отчёт принят | не входит в dump; это evidence, а не данные |
| Дампы базы | `/opt/finspace/backups/database` | нет (копия истины) | ежедневный backup | **`backup-cleanup.sh`**: 7 daily + 4 weekly | ничего; политику менять через `BACKUP_RETENTION_*` | **это и есть DR** |
| Backup sets | `/opt/finspace/backups/sets` | нет | по одному set на dump | **`backup-set-cleanup.sh`**: set живёт ровно столько, сколько дамп, на который он ссылается | ничего | опись и свидетельство проверки |
| Отчёты live-приёмки | `/opt/finspace/backups/acceptance-reports` | нет | приёмка Google-интеграции | **никакого** — только оператор | архивировать вручную | не входит в dump |
| `backups/restore-tests` | `/opt/finspace/backups/restore-tests` | нет | **ничего в него не пишет** | — | пустой каталог-заглушка из ранних версий; ничего делать не нужно | нет |
| Redis | Docker volume `finspace_redis_data` | **нет** | счётчики ограничений, короткая защита от повторов, heartbeat | Redis (TTL ключей) + `appendonly` | том **одноразовый**: его можно потерять или пересоздать без потери финансовых данных | **не входит** в DR |
| n8n | Docker volume `finspace_n8n_data` | нет (необязателен) | история выполнений, owner-аккаунт, credentials | `EXECUTIONS_DATA_PRUNE=true`, `EXECUTIONS_DATA_MAX_AGE_HOURS=336` внутри n8n | при росте — уменьшить срок хранения выполнений в n8n | **не влияет** на восстановление финансовых данных |
| Логи контейнеров | Docker daemon, драйвер `json-file` | нет | вывод приложения | **хост**, а не Finspace | ограничить размер в `/etc/docker/daemon.json` (`log-opts`) | нет |
| Журнал systemd | journald (backup, reclamation) | нет | плановые задания | **хост**, `journald.conf` | `SystemMaxUse=` в `journald.conf` | нет |
| Образы и build cache Docker | Docker daemon | нет | пересборки при обновлениях | **хост** | `docker image prune` осознанно и вручную | нет |

## 3. Чего не делать никогда

- не удалять и не редактировать содержимое `finspace_postgres_data` — это и есть база; всё, что
  нужно, делается через SQL и Alembic;
- не удалять финансовые строки напрямую в SQL ради «уборки»: у операций, счетов, категорий,
  правил и целей есть soft-delete и версионирование, и приложение на это рассчитывает;
- не чистить `audit_log`: `backup_status` читает оттуда события `backup.created`,
  `backup.verified` и `backup.remote.copy`, и без них проверка backup ослепнет;
- не удалять дампы и backup sets вручную — этим занимаются `backup-cleanup.sh` и
  `backup-set-cleanup.sh`;
- не открывать права на `backups/database`: каталог остаётся `0700`, артефакты `0600 root:root`;
- не запускать `docker system prune -a`, `docker volume prune` и `docker compose down -v` —
  первые два способны снести тома, третий сносит их гарантированно;
- не считать `data/imports` резервной копией: файл разбирается один раз и больше не читается.

## 4. Что делать, если растёт конкретный домен

**База данных.** Посмотрите отчёт: он сортирует таблицы по полному размеру и показывает
отдельно данные и индексы. Рост финансовых таблиц — это работа приложения, а не проблема.

**Индексы больше данных.** Нормально для таблиц с многими индексами. Если это неожиданно —
проверьте, отрабатывает ли autovacuum (`pg_stat_user_tables`), и рассматривайте `REINDEX`
как отдельную согласованную операцию обслуживания, а не как часть диагностики.

**`audit_log` или `auth_sessions` доминируют.** Сегодня ими никто не управляет: строки
накапливаются с активностью. Это осознанное состояние, а не сбой. Введение политики удержания —
продуктовое решение, и данный отчёт существует в том числе чтобы его подготовить.

**Импорты доминируют.** Проверьте `scripts/import_staging_reclaim.py` без аргументов: он
покажет, сколько занято и сколько подлежит освобождению. Если велики `import_rows` — это
provenance импортов, часть финансовой истории, а не мусор.

**Backup доминируют.** Так и должно быть: 7 ежедневных плюс 4 еженедельных копии базы. Если
это слишком много для диска, меняйте `BACKUP_RETENTION_DAILY` / `BACKUP_RETENTION_WEEKLY`,
а не удаляйте файлы руками.

**Свидетельства приёмки доминируют.** `data/acceptance` и `backups/acceptance-reports`
принадлежат оператору. Перенесите старые отчёты в архив за пределы сервера — автоматика их не
трогает намеренно.

**Логи Docker или journald доминируют.** Это граница хоста, а не приложения. Finspace
намеренно не содержит своей подсистемы ротации логов: ограничения задаются в
`/etc/docker/daemon.json` и `journald.conf`.

**Появилась незнакомая таблица.** Отчёт пометит её как `unclassified` и выдаст предупреждение.
Это ожидаемое поведение после новой миграции: таблицу нужно классифицировать в
`backend/app/services/data_lifecycle.py`, и тест `test_every_application_table_is_classified`
не даст забыть об этом. Неизвестная таблица **никогда** не получает политику удаления по
умолчанию.

## 5. Границы отчёта

- **Точка во времени.** Запись в базу во время отчёта не останавливается. Числа строк —
  собственные оценки PostgreSQL (`pg_stat_user_tables.n_live_tup`), а не `COUNT(*)`: точный
  подсчёт означал бы полное сканирование каждой таблицы, что для диагностики роста не нужно.
  Пока autovacuum ни разу не проанализировал таблицу, её оценка равна нулю — так бывает на
  только что созданной или только что восстановленной базе. Отчёт намеренно не запускает
  `ANALYZE` сам: это была бы запись, а он только читает.
- **Backup только описываются.** Отчёт показывает записанные факты последнего set
  (`alembic_revision`, `local_verified`, `offhost_verified`) и **не** объявляет копию годной.
  Годность доказывают `verify-backup.sh` и `/api/v1/automation/backup/status`.
- **Backup не измеряются из контейнера.** Каталог `0700 root`, backend работает без привилегий,
  поэтому размеры копий считает только хостовый скрипт. Нечитаемый каталог отмечается как
  `UNREADABLE`, а не как «0 байт».
- **Частичный отчёт не притворяется полным.** Любой нечитаемый раздел даёт `PARTIAL` и ненулевой
  код возврата; недоступная база — ненулевой код без каких-либо догадок.
- **Полнота подсчёта отделена от читаемости.** У каждого управляемого каталога в JSON есть два
  отдельных признака: `readable` и `complete`. Каталог может быть прекрасно читаемым, но
  посчитанным лишь частично — упёрлись в лимит обхода, внутрь вложенных каталогов отчёт
  намеренно не спускается, отдельная запись не поддалась `stat`, symlink не разыменовывается.
  В таком случае итог — **нижняя граница**: в человеко-читаемом выводе он печатается как
  `>= N`, статус помечается `PARTIAL`, а в `warnings` появляется `path_partial`. Неизвестные
  байты никогда не превращаются в ноль.
- **Битая символическая ссылка — это отказ, а не «каталога нет».** Проверка `is_symlink()` идёт
  раньше проверки существования, потому что последняя разыменовывает ссылку: иначе оборванная
  ссылка выглядела бы как честный ноль. Такой каталог даёт `readable=false`, `complete=false` и
  предупреждение `path_unreadable`.
- **n8n не требуется.** Ядро отчёта работает, даже если n8n выключен или падает в цикле.
  Credentials не читаются и не экспортируются никогда.
