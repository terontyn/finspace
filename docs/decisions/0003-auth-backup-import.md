# ADR 0003: локальная auth-модель, backup и staging-import

- Статус: принято
- Дата: 2026-07-22

## Контекст

Финансовое ядро этапа 2 доверяет development-заголовкам и не имеет механизма
восстановления или безопасной загрузки внешних данных. До интеграции Google Sheets нужны
проверяемая граница аутентификации, резервные копии и импорт без прямой записи в журнал.

## Решение по аутентификации

Используется короткоживущий JWT access token с алгоритмом HS256 и opaque refresh token.
Пароли хэшируются Argon2id. Access token хранится frontend только в памяти. Refresh token
передаётся cookie `HttpOnly`, `SameSite=Lax`; `Secure` включается автоматически в
production. В БД хранится только SHA-256 hash криптографически случайного refresh token.

Cookie содержит идентификатор сессии и случайный секрет. При refresh создаётся новая
сессия, старая помечается revoked и ссылается на замену. Повторное использование старого
токена считается компрометацией и отзывает активные сессии пользователя. Logout отзывает
текущую сессию, logout-all — все сессии пользователя.

SameSite=Lax не отправляет refresh cookie в cross-site POST. Дополнительно refresh и
logout проверяют заголовок `Origin`, если браузер его передал, по точному списку
`CORS_ORIGINS`. Это защищает cookie endpoints без хранения CSRF-secret в JavaScript и
сохраняет возможность локальной CLI-проверки без Origin.

Access JWT определяет пользователя. `X-Workspace-ID` является только выбором workspace:
membership всегда проверяется backend. Без заголовка выбирается первый доступный
workspace. Development-заголовки доступны лишь при `ALLOW_DEV_AUTH_HEADERS=true`, только
в development, и по умолчанию выключены.

Роли проверяют reusable dependencies: member — чтение, editor — изменение финансовых
данных и импорт, owner — управление участниками и критические операции. Audit доступен
editor и owner.

## Решение по резервному копированию

Backup выполняется официальными `pg_dump`/`pg_restore` из отдельного Compose service в
custom format. Dump сопровождается SHA-256 manifest. Restore по умолчанию использует
отдельную БД; перезапись основной требует отдельного флага и точного подтверждения.
Автоматическая verify-команда создаёт временную БД, восстанавливает dump, проверяет
Alembic revision и основные таблицы, затем удаляет только эту временную БД.

## Решение по импорту

CSV и XLSX проходят staging-таблицы `import_batches` и `import_rows`. Upload не создаёт
transactions. После явного mapping validate нормализует строки, разрешает счета и
категории по точному нормализованному имени и вычисляет детерминированный fingerprint.
Aliases пока не вводятся: неизвестные и неоднозначные имена остаются ошибками, новые
справочники молча не создаются.

Commit принимает idempotency key, создаёт только valid rows одной DB-транзакцией и
связывает их с batch. Rollback soft-delete только неизменённые после импорта операции;
изменённые дают конфликт без явного force. XLSX читается в read-only/data-only режиме,
поэтому формулы, макросы и внешние связи не исполняются.

## Последствия

- браузер больше не хранит доверенные user/workspace identifiers;
- JWT secret должен быть безопасным вне development;
- refresh rotation требует состояния PostgreSQL, а rate limiting — Redis;
- импорт занимает дополнительное место до применения retention policy;
- backup остаётся локальным и ещё не защищает от потери всего компьютера;
- Google Sheets, Drive, n8n и банковские интеграции остаются вне этапа 3.
