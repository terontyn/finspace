# ADR 0001: локальная Docker Compose-архитектура

- Статус: принято
- Дата: 2026-07-22

## Контекст

Проекту нужна повторяемая локальная основа для Windows/Docker Desktop, Linux и будущего
MSI Cubi. Предметная финансовая модель ещё не утверждена, а публичная эксплуатация,
Google-интеграции и автоматизации находятся вне первого этапа.

## Решение

Начать с локальной разработки в Docker Compose. Разделить Next.js, FastAPI, PostgreSQL,
Redis и Adminer на контейнеры в одной проектной сети. Публиковать development-порты только
на loopback хоста. Хранить PostgreSQL в named volume и управлять схемой исключительно
явными Alembic-миграциями.

PostgreSQL станет источником финансовой истины. Google Sheets позднее будет
синхронизируемым представлением для удобного просмотра и ввода, но не равноправной БД.
Redis не хранит долговременную финансовую истину.

MSI Cubi рассматривается как будущий production-сервер после добавления авторизации,
TLS/reverse proxy, секрет-хранилища, резервных копий и наблюдаемости. Текущий Compose-файл
остаётся development-конфигурацией.

## Последствия

Положительные:

- одинаковые Linux-контейнеры на Windows и Linux;
- явные сетевые и storage-границы;
- воспроизводимые миграции и изолированная тестовая БД;
- можно наращивать доменную модель без смены базовой платформы.

Компромиссы:

- Docker Desktop обязателен и потребляет дополнительные ресурсы;
- development Compose не является production deployment;
- Google Sheets и n8n не дают ценности до следующих этапов;
- backup/restore пока только архитектурное требование, а не реализованный процесс.

## Отклонённые варианты

- SQLite: не соответствует будущей конкурентной и серверной модели.
- Google Sheets как основная БД: недостаточные транзакционные гарантии и контроль схемы.
- Kubernetes: избыточен для локального foundation-этапа.
- Автоматическая миграция в каждом backend-процессе: создаёт риск параллельного запуска и
  скрытых изменений схемы.
