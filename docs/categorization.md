# Categorization preview lifecycle

Составление списка (preview) — это снимок предложений, а не изменение данных. Preview никогда не
меняет финансовое состояние.

- новый preview логически пригоден **24 часа** (`PREVIEW_TTL`);
- логическое истечение авторитетно **для новых apply-операций**: после `expires_at` попытка начать
  новую операцию по этому preview получает `410 CATEGORIZATION_PREVIEW_EXPIRED`;
- физическое удаление строки может произойти позже логического истечения — его выполняет
  `categorization-prune`, ограниченными пакетами;
- после физического удаления тот же запрос отвечает `404 CATEGORIZATION_PREVIEW_NOT_FOUND`.
  Preview чужого workspace и никогда не существовавший preview дают тот же `404` — отличить их
  нельзя;
- переход `410 → 404` — принятое следствие сборки мусора: оба ответа терминальные и ничего не
  меняют.

# Apply idempotency

Каждый `POST /api/v1/categorization-previews/{id}/apply` обязан нести `X-Idempotency-Key`.

- ключ идентифицирует **одну каноническую заявку**: workspace, preview и множество item id.
  Порядок item id не важен — они сортируются перед хешированием, поэтому та же выборка в другом
  порядке остаётся тем же логическим запросом;
- повторное использование ключа для другой заявки — `409 CATEGORIZATION_IDEMPOTENCY_CONFLICT`;
- каждый item выполняется в собственной транзакции, и мутация операции, её версия, запись аудита,
  событие sync-outbox и терминальный результат item фиксируются **одной транзакцией**. Поэтому
  зафиксированный результат и совершённая мутация не могут разойтись;
- **сохранённые терминальные результаты воспроизводятся, а не выполняются повторно.** Повтор с тем
  же ключом возвращает уже записанные результаты и не трогает финансовые данные;
- ответ упорядочен по порядку item id, присланному текущим вызовом.

# Incomplete apply recovery

Операция создаётся со статусом `in_progress` до обработки первого item и переводится в `completed`
только когда у каждого запрошенного item есть терминальный результат. Процесс, упавший в середине,
оставляет операцию, у части items которой результаты уже терминальны, а остальные просто не были
предприняты.

- повтор с тем же ключом **намеренно не перепроверяет логический TTL**: заявитель должен иметь
  возможность довести прерванный запрос до конца;
- незавершённая операция удерживает свой preview от физической уборки, но **не бесконечно**:
  защита заканчивается через `CATEGORIZATION_APPLY_RECOVERY_SECONDS` после `preview.expires_at`
  (по умолчанию 24 часа). Граница включающая;
- значение по умолчанию — ещё одно время жизни preview: продукт уже считает, что предложение
  осмысленно 24 часа, и незавершённая операция получает ровно один такой срок на восстановление.
  Максимальное физическое хранение preview — примерно «создание + 24 ч TTL + 24 ч окна»;
- пока preview физически существует, повтор может обработать непредпринятые items;
- после уборки preview: операция **остаётся `in_progress`** (новый статус не вводится),
  зафиксированные результаты сохраняются и по-прежнему воспроизводятся, а любой непредпринятый item
  получает `not_found` с `transaction_id = null`;
- операция, у которой все items уже терминальны, может перейти в `completed` и после уборки
  preview — для этого данные preview не нужны;
- **финансовая мутация никогда не выводится и не восстанавливается из отсутствующих данных
  preview.** Ни один item не применяется без действующей проверки версий операции, правила,
  категории и набора правил.

Окно настраивается только на стороне backend (`CATEGORIZATION_APPLY_RECOVERY_SECONDS`, 300…2592000
секунд) и не публикуется в API и frontend.

# Apply ledger retention

- строки `categorization_apply_operations` и `categorization_apply_results` **сейчас не имеют
  автоматической очистки**;
- это описание текущего состояния реализации, а **не обещание постоянного архива**;
- сохранённые терминальные результаты воспроизводятся детерминированно, пока apply-журнал
  сохраняется; политики его очистки в Finspace пока нет;
- «История применений» в интерфейсе — операционный журнал, а не аудит-грейд постоянная история;
- будущий релиз может задать явную политику хранения. До этого никакие обещания о сроках хранения
  давать нельзя.
