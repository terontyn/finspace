# Учение по восстановлению: чистая среда

Этот документ — процедура **F004**. Он доказывает одно утверждение целиком:

> проверенный backup set + внешне сохранённые секреты + точный релиз Finspace
> → чистая PostgreSQL → восстановленные финансовые данные → совместимая схема
> → работающие backend/frontend/worker → вход в систему и проверка данных.

Каждый шаг выполняется на **одноразовой чистой Linux-машине**. Работающий production
не является средой учения ни при каких условиях.

> [!IMPORTANT]
> Учение **не** доказывает автоматический перенос копий на отдельный хост. Это F003, и она
> остаётся отложенной, пока не введено отдельное хранилище. Здесь backup set переносится
> вручную — этого достаточно для доказательства восстановления и недостаточно для
> доказательства второго домена отказа. Не смешивайте эти две приёмки.

Установка чистого хоста описана в [production-install.md](production-install.md), контракт
резервных копий — в [backup-and-restore.md](backup-and-restore.md), правила совместимости
релиза и схемы — в [upgrade.md](upgrade.md). Здесь они соединены в один сценарий.

## 0. Инструменты

| Команда | Где выполняется | Что делает |
|---|---|---|
| `scripts/dr-restore-drill.sh candidates` | источник или drill-хост | показывает наборы, ничего не выбирает |
| `scripts/dr-data-probe.sh` | внутри tools-контейнера | безопасный read-only снимок: только счётчики |
| `scripts/dr-restore-drill.sh preflight` | drill-хост, до создания состояния | чистота хоста, пригодность набора, совместимость |
| `scripts/dr-restore-drill.sh restore` | drill-хост, БД пустая | восстановление через существующий `restore.sh` |
| `scripts/dr-restore-drill.sh verify` | drill-хост, приложение поднято | health, схема, сверка данных, вердикт |

Собственной реализации восстановления PostgreSQL здесь нет: авторитетным остаётся
`scripts/restore.sh`, вызываемый в существующем tools-контейнере.

Все три фазы пишут в **один** файл доказательств и выполняются строго по порядку: `restore`
отказывается работать без пройденного `preflight`, `verify` — без пройденного `restore`.
Причина не формальная: доказать, что хост был чист, можно только **до** того, как учение
само создало на нём контейнеры и тома.

## 1. SOURCE: подготовка на production

Цель — получить свежий проверенный набор и **сопоставимый** снимок финансовых счётчиков.

### 1.1 Зафиксировать текущий релиз

```bash
cd /opt/finspace
git rev-parse HEAD
git describe --exact-match --tags HEAD || echo "не тег: плавающий checkout"
./scripts/git-status-strict.sh
```

### 1.2 Остановить запись (короткое окно)

Снимок счётчиков и дамп должны относиться к одному логическому моменту. Иначе сравнивать их
нельзя, и делать вид, что можно, — хуже, чем не сравнивать вовсе.

```bash
sudo finspace-compose stop frontend backend sync-worker categorization-prune
```

**PostgreSQL и Redis не останавливаются.** `pg_dump` снимает согласованный транзакционный
снимок с работающей БД; останавливать сервер ради обычного backup не нужно и вредно.

n8n трогать не требуется: он пишет только через Backend Automation API, а backend уже
остановлен. Если хотите чистый журнал — остановите и его тем же способом.

### 1.3 Снять безопасный снимок счётчиков

```bash
sudo finspace-compose --profile tools run --rm backup sh /scripts/dr-data-probe.sh \
  > "/opt/finspace/data/acceptance/dr-source-probe-$(date -u +%Y-%m-%dT%H%M%SZ).json"
```

В файле только количества строк, одна временная метка последней операции и Alembic revision.
Имён, описаний, комментариев, адресов, номеров счетов, токенов и секретов там нет и быть не
должно — файл предназначен для чтения человеком и для приложения к отчёту.

Счётчики `audit_log`, `auth_sessions`, `sync_outbox` и `sync_inbox` попадают в раздел
`informational` и **не сравниваются**: сам конвейер backup дописывает в исходную базу события
`backup.created`, `backup.verified` и `restore.verified` уже после снятия дампа.

### 1.4 Создать свежий проверенный backup

```bash
sudo systemctl start finspace-backup.service
journalctl -u finspace-backup.service -n 200 --no-pager
```

Прогон обязан дойти до `backup_run_finished`. `local_verified=true` означает, что дамп был
восстановлен во временную базу и сверен по revision, таблицам и колонкам, — совпадения SHA-256
для этого недостаточно.

### 1.5 Вернуть запись

```bash
sudo finspace-compose start backend sync-worker categorization-prune frontend
curl -fsS http://127.0.0.1:8000/api/v1/health/ready
```

Окно закрыто. Дальше production работает как обычно, а учение идёт на другой машине.

### 1.6 Выбрать набор явно

```bash
sudo /opt/finspace/scripts/dr-restore-drill.sh candidates --backup-root /opt/finspace/backups
```

Команда только показывает. Выбор всегда делает оператор: «последний по времени» не является
основанием.

```bash
SET_ID="ВЫБРАННЫЙ_SET_ID"
sudo cat "/opt/finspace/backups/sets/$SET_ID/backup-set.json"
sudo cat "/opt/finspace/backups/sets/$SET_ID/backup-set-report.json"
```

Выпишите `alembic_revision`, `finspace_commit`, `finspace_tag` и `sha256`: по ним выбирается
релиз для drill-хоста.

### 1.7 Собрать переносимый набор

Раскладка ровно та же, которую готовит `backup-offhost.sh`, поэтому набор, приехавший по
будущей автоматической внешней копии, и набор, перенесённый руками, неразличимы.

```bash
SET_ID="ВЫБРАННЫЙ_SET_ID"
STAGING="/root/dr-transfer/$SET_ID"
sudo install -d -m 0700 -o root -g root "$STAGING"
sudo cp "/opt/finspace/backups/database/finspace_${SET_ID}.dump" "$STAGING/database.dump"
sudo cp "/opt/finspace/backups/database/finspace_${SET_ID}.dump.manifest.json" \
  "$STAGING/database.manifest.json"
sudo cp "/opt/finspace/backups/sets/$SET_ID/backup-set.json" "$STAGING/"
sudo cp "/opt/finspace/backups/sets/$SET_ID/backup-set-report.json" "$STAGING/"
sudo sh -c 'cd "$1" && sha256sum -- * >SHA256SUMS' sh "$STAGING"
sudo cat "$STAGING/SHA256SUMS"
```

Если в наборе есть холодный архив n8n и вы собираетесь его проверять, скопируйте туда же
`n8n-data.tar.gz` и `n8n-data.sha256` **до** формирования `SHA256SUMS`.

> [!WARNING]
> В переносимый набор **не** входит `.env`. Секреты никогда не кладутся в архив резервной
> копии и не едут тем же каналом. См. раздел 3.

## 2. TRANSFER: перенос

Канал выбирает оператор: `scp`, `rsync` поверх SSH или офлайн-носитель. Документация не
назначает адрес приёмника — отдельного хранилища ещё нет, а выдуманный хост хуже, чем его
отсутствие.

```bash
# Пример: SSH. Адрес и учётная запись — ваши.
sudo tar -C /root/dr-transfer -cf - "$SET_ID" | ssh <drill-host> 'tar -C /var/tmp -xf -'
```

На drill-хосте **обязательно** повторить сверку после переноса:

```bash
cd "/var/tmp/$SET_ID"
sha256sum -c SHA256SUMS
```

Переносится только выбранный набор. Другие копии, каталог `/opt/finspace/backups` целиком и
тем более `.env` не переносятся.

## 3. Секреты: отдельная опись, отдельный канал

Backup **не содержит** секретов восстановления, и это сделано намеренно. Оператор берёт их из
внешнего хранения (менеджер паролей или файл, зашифрованный `age`/`gpg`, на отдельном
носителе) и создаёт `.env` на drill-хосте вручную.

| секрет | если он есть | если его нет |
|---|---|---|
| `POSTGRES_PASSWORD` | новый кластер инициализируется им | **любое** значение годится: это конфигурация доступа, а не шифрование данных на диске; важно лишь, чтобы `DATABASE_URL` совпадал |
| `JWT_SECRET_KEY` | прежние сессии остаются валидными | пользователи входят заново; **финансовые данные не теряются**. Вход по паролю работает в любом случае: пароли лежат в дампе как Argon2id-хэши |
| `GOOGLE_TOKEN_ENCRYPTION_KEY` + `_VERSION` | сохранённые Google-токены расшифровываются | Google-подключения требуют повторной авторизации; **финансовые данные не теряются** |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | OAuth-provider работает | нужны только необязательному OAuth-провайдеру |
| `N8N_ENCRYPTION_KEY` | credentials n8n расшифровываются | credentials создаются заново; workflow лежат в Git |

**Ни один из этих случаев не является провалом приёмки F004.** Восстановление финансовых
данных не зависит ни от Google, ни от n8n, ни от совпадения JWT-секрета. Что именно было
доступно — фиксируется в отчёте.

Значения секретов не печатаются, не логируются и не попадают в файл доказательств. Учение
не читает production `.env` и не переносит его.

## 4. CLEAN DRILL HOST: подготовка

Одноразовая Linux-VM или отдельный чистый хост. До начала на нём не должно быть:

- контейнеров Finspace;
- томов `finspace_postgres_data`, `finspace_redis_data`, `finspace_n8n_data`;
- прежнего `.env`;
- прежнего wrapper `finspace-compose`;
- какой-либо зависимости от `/etc/finspace/compose.server.yml`;
- операторских алиасов и недокументированных ручных правок.

Требование — **отсутствие состояния Finspace**, а не пустой Docker-хост: посторонние
контейнеры и тома других приложений учению не мешают и не проверяются.

Пройдите [production-install.md](production-install.md), разделы 1–7:

1. предварительные требования;
2. каталоги и учётная запись оператора;
3. чистый `git clone` в `/opt/finspace`;
4. **точный релиз**, совместимый с `alembic_revision` набора (раздел 6 ниже);
5. `.env` из внешнего хранения, `root:root 0600`;
6. `sudo ./scripts/install-finspace-compose.sh`;
7. `sudo ./scripts/prepare-runtime-storage.sh /opt/finspace`.

Для учения на localhost без HTTPS в `.env` задайте:

```env
AUTH_COOKIE_SECURE=false
CORS_ORIGINS=http://localhost:3000
```

Иначе браузер не отправит cookie обновления сессии по `http://`, и вход «не получится» по
причине, не имеющей отношения к восстановлению.

Затем проверьте топологию — **до** создания какого-либо состояния:

```bash
cd /opt/finspace
sudo finspace-compose config --quiet
sudo finspace-compose config --format json |
  python3 backend/scripts/validate_compose_topology.py production --stdin
```

### 4.1 Доказательство чистоты и preflight

Выполняется, пока на хосте ещё ничего не создано:

```bash
sudo /opt/finspace/scripts/dr-restore-drill.sh preflight \
  --set-dir "/var/tmp/$SET_ID" \
  --confirm-clean-environment
```

Preflight фиксирует и проверяет:

- контейнеры проекта `finspace` — 0; тома `finspace_*` — 0;
- был ли `finspace-compose` установлен до этого;
- присутствует ли на хосте `/etc/finspace/compose.server.yml`;
- набор: наличие всех файлов, совпадение SHA-256 дампа с обоими манифестами, согласие
  манифестов о revision, `local_verified=true`, наличие commit, безопасность `set_id`;
- при наличии `SHA256SUMS` — сверку всего набора после переноса;
- целевой checkout: commit, tag, Alembic head, прочитанный прямо из графа миграций;
- случай совместимости A/B/C.

Отказ на этом шаге — правильный исход, а не препятствие. Файл доказательств пишется в любом
случае, с вердиктом `FAILED` и машинной причиной.

## 5. Порядок восстановления PostgreSQL

Порядок один и обсуждению не подлежит:

```
чистая PostgreSQL -> восстановление выбранного проверенного дампа
                  -> проверка Alembic revision
                  -> при необходимости миграция вперёд
                  -> запуск приложения
```

**Нельзя:** инициализировать данные приложения и «влить» восстановление поверх; выполнять
миграции дальше уровня backup **до** восстановления; понижать схему после восстановления.

```bash
cd /opt/finspace
sudo finspace-compose up -d postgres redis
sudo finspace-compose ps
```

Поднимается **только** состояние. Backend, frontend и worker-процессы ещё не стартуют: пустая
база не должна быть заполнена приложением до восстановления.

```bash
sudo /opt/finspace/scripts/dr-restore-drill.sh restore \
  --set-dir "/var/tmp/$SET_ID" \
  --confirm-clean-environment \
  --evidence /opt/finspace/data/acceptance/dr-restore-<DRILL_ID>.json
```

Путь к файлу доказательств — тот же, что напечатал preflight: фазы продолжают один отчёт.

Что делает фаза `restore`:

1. требует пройденного preflight в этом же отчёте;
2. повторно проверяет набор;
3. копирует дамп и манифест в `/opt/finspace/backups/database/` — единственный каталог, из
   которого `restore.sh` принимает файл, — и **заново сверяет SHA-256 после копирования**;
4. **отказывается**, если целевая база не пуста. Это главный предохранитель: в production
   база никогда не пуста, поэтому случайный запуск учения там останавливается здесь;
5. вызывает существующий `restore.sh` в tools-контейнере;
6. сверяет revision восстановленной базы с revision набора;
7. в случае B выполняет `alembic upgrade head` образом целевого релиза — **только после**
   восстановления — и проверяет, что достигнут head.

### Redis

Redis одноразовый. Учение стартует с пустого тома Redis, копировать и восстанавливать его
**не нужно никогда**. В нём живут только счётчики ограничений, короткая защита от повторов и
heartbeat; финансовых данных там нет.

## 6. Совместимость релиза и схемы

Релиз drill-хоста выбирается по `alembic_revision` набора, а не наоборот.

| соотношение | случай | действие |
|---|---|---|
| revision набора = head целевого релиза | **A** | восстановить и запустить |
| revision набора старее, но присутствует в целевом релизе | **B** | восстановить, затем `alembic upgrade head` образом целевого релиза |
| revision набора новее, чем поддерживает целевой релиз | **C** | **отказ**: выбрать релиз, который содержит эту ревизию |

`alembic downgrade` не применяется никогда. Приложение не запускается на схеме, которую оно
не поддерживает. Случай C определяется механически: ревизия набора отсутствует среди
миграций целевого checkout — значит, backup новее релиза.

Проще всего проводить учение в случае A: взять релиз, соответствующий `finspace_tag` или
`finspace_commit` набора. Случай B проверяется отдельно и осознанно.

## 7. START: запуск приложения

```bash
cd /opt/finspace
sudo finspace-compose build backend sync-worker categorization-prune frontend
sudo finspace-compose up -d --no-deps backend
curl -fsS http://127.0.0.1:8000/api/v1/health/ready

```

Миграции здесь **не** запускаются: схема уже приведена в нужное состояние фазой `restore`.

## 8. VERIFY: автоматическая часть

```bash
sudo /opt/finspace/scripts/dr-restore-drill.sh verify \
  --set-dir "/var/tmp/$SET_ID" \
  --confirm-clean-environment \
  --evidence /opt/finspace/data/acceptance/dr-restore-<DRILL_ID>.json \
  --source-probe /var/tmp/dr-source-probe-<...>.json
```

Проверяется:

- production-топология через validator;
- `postgres`, `redis`, `backend`, `frontend`, `sync-worker`, `categorization-prune` — запущены;
- `GET /api/v1/health` и `GET /api/v1/health/ready`;
- `GET /login` frontend;
- `alembic current` равен head целевого релиза;
- снимок счётчиков восстановленной базы и его **построчная сверка** со снимком источника.

Расхождение любого сравниваемого счётчика — провал, а не предупреждение. Если `--source-probe`
не передан, в отчёте будет честное `not_compared`: снимок, снятый в другой логический момент,
сравнению не подлежит и не выдаётся за сравнение.

### 8.1 Операторская часть — обязательна

Автоматический вердикт **не является** приёмкой F004. Пароли в автоматизацию не передаются.

1. Откройте `http://127.0.0.1:3000/login` и войдите под учётной записью, существовавшей в
   резервной копии. Пароль работает и при новом `JWT_SECRET_KEY`: он проверяется по
   Argon2id-хэшу из дампа.
2. Просмотрите в UI репрезентативные восстановленные данные: список счетов и остатки,
   последние операции, категории, бюджет и закрытые периоды.
3. Убедитесь, что цифры соответствуют production на момент снятия копии.
4. Впишите результат этих двух шагов в отчёт (`operator_acceptance`), заменив `pending`.

Пока эти пункты не выполнены человеком, учение не пройдено.

### 8.2 Google

Финансовое восстановление не зависит от живого доступа к Google. Если исходный
`GOOGLE_TOKEN_ENCRYPTION_KEY` доступен, сохранённые токены должны расшифровываться
приложением. Если ключ намеренно недоступен, ожидается повторная авторизация — и это **не**
провал приёмки. Живая синхронизация в обязательную часть учения не входит: внешний API не
должен делать проверку восстановления нестабильной.

### 8.3 n8n — необязательная ветка

Ядро F004 от n8n не зависит. Если в наборе есть холодный архив и вы хотите его проверить:

1. остановите n8n;
2. восстановите **свежий** том `finspace_n8n_data` из `n8n-data.tar.gz` (сверив его SHA-256);
3. задайте исходный `N8N_ENCRYPTION_KEY`;
4. запустите n8n и проверьте локальный UI и состояние owner-аккаунта.

Экспорт credentials не выполняется. Telegram не является блокером Stage D. Если ветка
пропущена, в отчёте остаётся `n8n_restore: "not_tested"` — именно так, а не «пройдено».

### 8.4 Планировщик backup на drill-хосте

После восстановления приложения проверьте, что установочный контракт Stage C работает:
`finspace-backup.service` и `finspace-backup.timer` устанавливаются штатно. **Включать таймер
на одноразовом хосте необязательно** — цель учения восстановление, а не создание ещё одной
цепочки копий. F002 и F003 здесь не проверяются.

## 9. EVIDENCE: файл доказательств

Все три фазы пишут один JSON, атомарно (`.partial` → `mv`), по умолчанию в
`/opt/finspace/data/acceptance/dr-restore-<DRILL_ID>.json`. Это runtime-артефакт: в Git он не
попадает.

Что в нём есть: идентификатор и время учения, пройденные фазы, вердикт и машинная причина
отказа; состояние хоста до начала (контейнеры, тома, наличие wrapper и legacy-override);
`set_id`, имя дампа, SHA-256, `alembic_revision`, commit и tag набора, `local_verified` и
`offhost_verified`; commit, tag и Alembic head целевого релиза; случай совместимости; результат
восстановления, число таблиц до него, полученная revision и результат миграции; результаты
топологии, сервисов, health, `alembic current`; оба снимка счётчиков и результат сверки;
статус n8n; операторские пункты.

Чего в нём нет и быть не может: паролей, JWT, ключей шифрования, OAuth- и Telegram-секретов,
полного `compose config`, дампов окружения и любых строк финансовых данных.

Провал тоже создаёт отчёт — с `verdict: "FAILED"` и причиной. Учение, не оставившее следа,
не считается проведённым.

Прочитать отчёт (он `root:root 0600`):

```bash
sudo cat /opt/finspace/data/acceptance/dr-restore-<DRILL_ID>.json
```

## 11. CLEANUP

Выполняется **после** того, как отчёт прочитан и принят, и никогда раньше. Успешную среду
лучше оставить нетронутой до этого момента.

Убирается только то, что создало учение, и только на drill-хосте:

```bash
# 1. Сохраните отчёт и снимки за пределы одноразовой машины.
sudo cp /opt/finspace/data/acceptance/dr-restore-<DRILL_ID>*.json /var/tmp/keep/

# 2. Остановите и удалите контейнеры и тома ЭТОГО хоста.
cd /opt/finspace
sudo finspace-compose down
sudo docker volume rm finspace_postgres_data finspace_redis_data

# 3. Уберите перенесённый набор и checkout.
sudo rm -rf "/var/tmp/$SET_ID"
```

> [!CAUTION]
> Ни одна из этих команд не выполняется на production-хосте. `docker system prune -a`,
> `docker volume prune` и `docker compose down -v` в этой процедуре не используются: они
> способны задеть то, чего учение не создавало. Тома удаляются **поимённо**.
>
> Самый надёжный способ уборки — **уничтожить одноразовую VM целиком**. Тогда решать, что
> удалять, вообще не приходится.

Резервные копии на источнике не удаляются никогда: учение их только читает.

## 12. Автоматический режим для CI

`scripts/tests/dr-restore-drill.test.sh` проверяет контракт учения на поддельных `docker`,
`finspace-compose`, `git` и `curl` во временном каталоге. Он не трогает ни одного реального
контейнера, тома, базы или production-пути и удаляет только созданное им самим.

Флаг `--isolated-test-mode` разрешает запуск при уже существующем состоянии Finspace — для
репетиций и автоматических проверок на занятом хосте. Он **записывается в отчёт**
(`isolated_test_mode: true`, `clean_host_proven: false`) именно для того, чтобы такой прогон
нельзя было предъявить как приёмку чистой среды. Для F004 он неприменим.

## 13. Что закрывает и что не закрывает это учение

- **закрывает** при успешном прохождении: F004 — восстановление в чистой среде;
- **не закрывает**: F003 — физическую внешнюю копию на отдельный домен отказа. Ручной перенос
  доказывает восстановление, но не автоматический перенос;
- **не относится сюда**: F002 — плановые проверенные копии; они проверяются на production.
